# 技术架构文档

## 技术栈

| 层面 | 选型 | 理由 |
|---|---|---|
| Web前端 | Next.js | 与公司其他产品（含 Mindo）共用同一技术栈，便于多产品统一在同一根域名下的不同子域名部署；同时任务管理主页面（非登录后的部分）需要兼顾 SEO/GEO，Next.js 的 SSR 能力覆盖这个需求 |
| 移动端 | **React Native（通过 Expo）** | 产品对移动端的原生交互体验和视觉观感要求高，Capacitor 的 WebView 套壳方案无法满足；React Native 渲染真正的原生组件，Expo 是官方推荐的标准起步路径（EAS Build/Submit/Update） |
| 后端/云同步 | Supabase（PostgreSQL + Auth + Realtime + RLS） | 与另一产品 Mindo 技术栈一致，工具链熟悉；RLS原生支持多用户数据隔离 |
| 循环任务 | RFC 5545 RRULE 表达规则；日期推算是自己写的引擎（`packages/core/src/recurrence`），历法放在独立的模块里（以前用 rrule.js，已换掉，原因见下方"循环规则的日期推算"） | 业界标准，未来对接日历系统天然兼容；换历法只换历法模块 |
| 开发环境 | 电脑为主 | vibe coding 全流程用电脑执行 |

### 关于 Web 与移动端代码复用范围（重要调整）

早期方案（Next.js + Capacitor）设想 Web 和移动端复用同一套 UI 代码。改为 React Native 后，**这个前提不再成立**：React（Web）与 React Native（移动端）语法相似但不能直接复用界面代码，两端的表现层需要**各自独立实现**。

分层架构（见下）本身已经为此留出了空间：

- **表现层（Presentation）**：Web 和 Mobile 各自独立实现，两端各写一份
- **应用层 / 领域层 / 数据层**：与 UI 框架完全解耦的纯 TypeScript 代码，Web 和 Mobile **共享同一份**（紧迫度计算、象限判定、循环规则引擎、Supabase 通信、同步引擎等"脑子"部分不用重复实现）

## 架构原则

本项目遵循三条核心原则，目标是让未来新增功能、更换技术组件的成本尽量低：

### SRP（单一职责原则）

每个模块只负责一件事。例如：

- `UrgencyCalculator`：只负责紧迫度分档计算
- `RecurrenceEngine`：只负责循环任务下一次实例的计算与历史记录归档判定

### 循环规则的日期推算：为什么不用 rrule.js

规则仍用 RFC 5545 的 RRULE 存储和交换；把规则展开成一个个日期的部分，从 rrule.js 换成了自己写的引擎
（`recurrence-rule.ts` 负责 RRULE 的生成和解析，`recurrence-engine.ts` 负责推算，`calendar.ts` 是历法模块）。原因有两个：

1. **"没有这一天就落到最后一天"的标准写法**：每月 31 日、每年 2 月 29 日这类规则，产品要求没有这一天的月份落到当月最后一天。
   标准写法是 RFC 7529 的 `RSCALE=GREGORIAN;SKIP=BACKWARD`，rrule.js 不支持 RSCALE / SKIP，只会把没有这一天的月份跳过；
   在它外面打补丁会让存下来的规则和推算结果对不上。自己的引擎按这个写法直接推算，存的规则就是标准写法。
2. **以后接入其他历法**：rrule.js 绑死在公历（JavaScript 的 `Date`）上。自己的引擎只通过历法模块（`CalendarSystem`）
   回答"某个周期从哪天开始""这个月有几天""第几个星期几""ISO 第几周"这些问题，规则的结构"周期 + 周期里的位置"和历法无关；
   以后加农历等历法时只换历法模块，规则、引擎和存储都不用改。

另外，我们用到的只是 RRULE 的一个子集（日、周、月、年 + 周期里的位置，没有结束条件），自己实现很小，也去掉了一个依赖。
- `QuadrantClassifier`：只负责把（紧迫度，重要性）映射成象限标签
- `TaskRepository`：只负责任务数据的存取，不涉及业务规则判断

### ISP（接口隔离原则）

上层代码只依赖它需要的**窄接口**，不依赖具体实现细节：

- `ITaskRepository`：只暴露任务增删改查
- `IAuthProvider`：只暴露登录/登出/当前用户
- `ILocalStore` / `IRemoteStore` / `SyncEngine`：三者职责互相隔离，上层始终只调用统一的 `TaskRepository` 接口，感知不到背后是本地存储、远程Supabase还是同步队列
- **`QuadrantClassifier` 不感知任务是否为循环任务**：它只接收任务当前的「一个代表」（标准化的重要性/紧迫度字段），这个代表背后是普通任务还是循环任务的某次实例，对它而言是同一种输入形状。这样以后新增任何任务形态（例如未来的外部同步任务），矩阵逻辑都不需要改动

好处：未来更换后端服务、更换移动端技术方案、或新增任务形态，只需重新实现对应接口或新增适配，不影响核心业务代码。

### OCP（开闭原则）：对扩展开放，对修改关闭

**不为"未来可能用到"的功能预先在核心表/核心逻辑里占位。** 新功能应该通过「新增独立表」或「新增可空字段」实现。**上线后适用**：禁止修改现有必填字段的语义或约束（上线前可以直接改，见《迁库说明》里数据库的工作规则）。核心实体（Task）不感知任何扩展模块（团队协作、子任务、日历视图、外部任务源）的存在，扩展模块单向依赖核心，核心不反向依赖扩展。

判断标准：一个新想法能不能只用"新增表 / 新增可空字段"实现、不碰现有表的必填约束？能，直接加；不能，才需要架构级讨论。这也是评估《产品愿景与理念文档》中长期设想的统一标准。

## 分层架构

```
┌─────────────────────────────────┐
│  表现层 (Presentation)            │  Next.js (Web) / React Native+Expo (Mobile) —— 两端独立实现
├─────────────────────────────────┤
│  应用层 (Application/Use-Cases)   │  业务流程编排，不关心数据存储细节 —— Web/Mobile 共享
├─────────────────────────────────┤
│  领域层 (Domain/Core)             │  纯 TypeScript，零框架依赖 —— Web/Mobile 共享
│  Task实体、紧迫度计算、重要性分档、  │
│  象限判定、循环规则引擎             │
├─────────────────────────────────┤
│  数据层 (Data/Repository)         │  接口 + 具体实现（Supabase/本地存储）—— Web/Mobile 共享
└─────────────────────────────────┘
```

## 数据层设计（Offline-First）

移动端需要离线可用：无网络时可查看/新建任务，联网后自动同步。

```
packages/data/
  ├── local/      本地存储实现（Web: IndexedDB；移动端: SQLite）
  ├── remote/     Supabase 通信
  ├── sync/       同步引擎：待同步队列 + 触发时机 + 冲突解决
  └── repository/ 组合以上三者，对外统一暴露 ITaskRepository
```

- `ILocalStore`：只管本地读写
- `IRemoteStore`：只管与 Supabase 通信
- `SyncEngine`：只管同步队列和触发时机（联网瞬间/定时/手动）
- 上层业务代码永远只调用 `TaskRepository`，不感知本地/远程/同步细节

**冲突解决策略（MVP阶段）**：Last-Write-Wins（以 `updated_at` 时间戳为准）。极端场景（两台设备同时离线编辑同一任务）可能丢失一方修改，个人任务管理场景概率低，可接受；后续如需要可升级为字段级合并。

## Monorepo 结构

延续 Mindo 项目的组织方式（pnpm + Turborepo）：

```
packages/core/     领域层，纯TS，无框架依赖
packages/data/     数据层实现（本地/远程/同步）
apps/web/          Next.js
apps/mobile/       React Native + Expo
```

## 时间与日历兼容性

**具体到时刻的时间存 UTC 时间戳；只到某一天的日期存日期**（数据库 `date` 类型，前端是 "YYYY-MM-DD" 字符串，不带时刻、不带时区）。

- 存 UTC 时间戳的：创建、完成、确认、改动的时刻，通知时间等（`*_at`）
- 存日期的：截止日期 `deadline_on`、循环的开始日期 `recurrence_start_on`、每一次的日期 `occurrence_date`、任务关系的开始和结束 `start_on`
- "今天""逾期""这一次是否已经过去"都按用户本地的日期判断（`todayOf`：按用户时区取今天的日期），某一天过完才算过去
- 以后要加时刻：新增一个可以为空的时刻字段，日期保持不变

历法：存的都是公历日期。循环规则的日期推算通过历法模块（`packages/core/src/recurrence/calendar.ts` 的 `CalendarSystem`）进行，规则的结构"周期 + 周期里的位置"和历法无关；界面上的日历（`apps/web/src/lib/calendar-view.ts` 的 `CalendarView`，日历右上角留着切换历法的位置）同样可以替换。农历、伊斯兰历等以后作为新的实现加入，领域层和存储不变。

## 部署与地区

- 前端可以部署在 Vercel，也可以用根目录的 `Dockerfile` 在任何普通服务器上运行（Next.js 独立输出，`NEXT_OUTPUT=standalone`），见《部署说明》
- 部署地区 `NEXT_PUBLIC_REGION`（international / china）在构建时决定（`apps/web/src/lib/region.ts`）；china 只去掉 Google 登录。
  浏览器端除了登录和数据两个 Supabase 地址，不请求任何外部服务（系统字体，没有 CDN、统计、地图），所以中国大陆部署不需要额外替换资源
- 登录和数据既可以是两个 Supabase 项目（数据项目用第三方认证信任登录项目的令牌），也可以是同一个实例（用它自己的 Auth）
