# 核心算法与业务逻辑

## 0. 坐标方向（明确约定）

矩阵坐标系并非行业统一标准（Eisenhower 本人未曾绘制过矩阵图，后世不同来源的轴线分配也不一致），本项目明确约定：

- **X 轴（紧迫度）**：越靠右越紧急
- **Y 轴（重要性）**：越靠上越重要

## 1. 紧迫度（X轴）计算

### 理论依据

人类对时间/数值差异的感知遵循 **Weber-Fechner 定律**（对数感知定律）：感知差异与刺激的相对比例相关，而非绝对差值。这与「双曲线贴现」（Ainslie, 1975；Piers Steel 的时间动机理论）描述的现象在数学上是等价的——deadline 越近，紧迫感上升越剧烈；deadline 越远，紧迫感变化越平缓。

选刻度时参考过敏捷开发故事点估算用的斐波那契数列（相邻档位比例约为黄金比例 **φ ≈ 1.618**，同样基于 Weber-Fechner 定律）：越近的档位越密、越远越疏。**斐波那契只是挑选刻度时的参考，不是实际标尺**——实际标尺是按自然天、周、月、季度取的天数（见下表），更贴近日常说法（"一周内""一个月内"），也方便以后调整。

### 判档依据：剩余时间，而不是日历天数

- 剩余时间 **R = 截止时刻 − 现在**（精确到毫秒，折算为天，可带小数）
- 只选了日期的截止时间取**当天最后一刻**（23:59:59.999）；选了具体时刻的直接用该时刻；循环任务用当前代表实例（该实例当天的最后一刻）
- 一律按用户时区（日期型截止时间的"当天最后一刻"按用户时区确定）
- 区间**上界包含在内**，即 (a, b]；R ≤ 0 为逾期
- 例：现在 10:00，截止明天 09:00 → R = 23 小时 → (0, 1] 档；截止"明天"（全天）→ R ≈ 1.58 天 → (1, 2] 档；深夜 23:30 看一个 00:30 截止的任务 → R = 1 小时 → (0, 1] 档（不会因为跨过午夜就算"明天"）

### 紧迫度分档表（基本向量）

矩阵横轴共 **14 格，全部等宽**；中线落在"两周"这条分界线上（R = 14 天），左右各 7 格。越靠右越紧急：

| 序号 tier_index | 区间 R（天） | 分界刻度名（格子左边界） | 所在侧 |
|---|---|---|---|
| — | R ≤ 0 | 逾期（最右格，标在格子中央） | 紧急 |
| 0 | (0, 1] | 1天 | 紧急 |
| 1 | (1, 2] | 2天 | 紧急 |
| 2 | (2, 3] | 3天 | 紧急 |
| 3 | (3, 5] | 5天 | 紧急 |
| 4 | (5, 7] | 一周 | 紧急 |
| 5 | (7, 14] | 两周（中线） | 紧急 |
| 6 | (14, 21] | 三周 | 不紧急 |
| 7 | (21, 30] | 一个月 | 不紧急 |
| 8 | (30, 60] | 两个月 | 不紧急 |
| 9 | (60, 90] | 一季度 | 不紧急 |
| 10 | (90, 180] | 半年 | 不紧急 |
| 11 | (180, 270] | 三个季度 | 不紧急 |
| 12 | (270, 365] | 一年 | 不紧急 |

- 刻度名标在**分界线上**，不标在格子中央；从右到左依次为 1天、2天、3天、5天、一周、两周（中线）、三周、一个月、两个月、一季度、半年、三个季度、一年，最右边的格子标"逾期"
- 不紧急一侧的天数（21 / 30 / 60 / 90 / 180 / 270 / 365）按自然周、月、季度取值，集中在代码的具名常量里（`packages/core/src/urgency/tiers.ts`），调整刻度只改一处

**紧急/不紧急分界**：以中线为界，**R ≤ 14 天（含逾期）为「紧急」**，R > 14 天为「不紧急」。`QuadrantClassifier` 按同一规则判定象限。

### 扩展向量（超过一年）

| 区间 R（天） | 说明 |
|---|---|
| (365, 730] | 两年内 |
| (730, 1095] | 三年内 |
| (1095, 1825] | 五年内 |
| (1825, 2555] | 七年内 |
| (2555, 3650] | 十年内 |

同样是自然值。紧迫度数值上仍按此延伸计算，但 **R > 365 天的任务不进入矩阵可视化展示**（矩阵图上不显示远期任务），仅在列表视图中正常呈现。

### 边界情况处理

- **无截止时间**：紧迫度归入最大档（不紧急端的最远端，即最左格），任务仍可基于重要性进入矩阵展示（除非重要性也是0档，见第3节边界情况）
- **已逾期**（R ≤ 0，未完成）：紧迫度持续超出边界（不封顶）。矩阵展示上，逾期任务放在**最右格**，标红显示，并标注具体逾期天数（**逾期天数按日历天计算**；当天稍早已过截止时刻的显示"今天已过"）；这个展示状态维持 **3 天**，3天后任务从矩阵图上退场（进入"已错过"状态，仅列表可见，不再是矩阵展示层面的事，与"错过"状态判定本身无关——错过状态在超过截止时间的那一刻就已成立，3天只是矩阵图上的展示宽限期，见第5节）
- 逾期任务在矩阵上的标签：点位只有一个，在标签内部的右端（分类颜色，多分类按切片，外加红色外圈），标题在点位左边向左伸展，并与其他任务的标签避让；放不下时先缩短标题，再放不下并入"+N"

### 关键实现原则

紧迫度**不是**创建任务时计算一次存死的值，而是**每次展示时基于当前时间动态计算**（因为距截止时间的天数会随时间推移变化）。

## 2. 重要性（Y轴）

- 用户手动选择，共 **0-5，六档**
- **0 档 = 未设置**（替代原先的 `null`，任务创建时默认落在此档，用户不主动设置重要性即保持0档）
- 1-5 档为用户主动设置的档位，无高低位划分，矩阵上每一档对应 Y 轴一条固定区间，任务在该区间内自由散布，不强制对齐某个精确坐标点
- 矩阵纵轴共 6 格：刻度 0 到 5 标在分界线上，重要性 N 落在标 N 那条线上方的一格（N = 5 是最上面一格，顶端不再标"6"）；中线在刻度 3 上，下面三格是 0、1、2（不重要），上面三格是 3、4、5（重要）

## 3. 象限判定逻辑与矩阵展示规则

- 象限是根据「紧迫度所属区（紧急/不紧急）× 重要性所属区（重要/不重要）」计算得出的展示分组，不存储为任务字段，属于查询/展示层的派生逻辑
- **四个象限均为合法区域**，包括"不重要且不紧急"——一个重要性=1、紧迫度落在不紧急区的任务，会正常显示在矩阵左下角区域，这不代表它被排除
- **唯一不进入矩阵坐标系的情况**：重要性为 0 档（未设置）**且**紧迫度对应"无截止时间"（两者都未被用户处理）。只要用户设置了重要性或截止时间中的**任意一项**，任务就会正常出现在矩阵上
- 远期（扩展向量，超过一年）任务不进入矩阵可视化，即使有明确的重要性设置
- 矩阵图不绘制可见网格线，格子仅为逻辑上的坐标范围；同一（重要性区间 × 紧迫度区间）内的多个任务自动散布/避让，避免视觉重叠

## 4. 分类（多对多）

- 一个任务可同时归属**多个**分类，数据层面是标签（多对多关系），但 UI 呈现上让用户感觉是"归属"体验（参考邮箱的多收件箱模式：删除分类只解除关联，不影响任务本身存续）
- 每个分类需要一个**颜色属性**，用于矩阵中任务圆点的分色标识：
  - 提供默认调色板候选（起步九色：红黄蓝、橙绿紫、粉棕青），颜色之间视觉独立性强
  - 提供自定义调色板（优先级低，可复用现成的颜色选择组件）
  - 颜色需在用户的分类集合内**排他，不重复**；调色板耗尽后的处理方式留待实现阶段决定（建议方向：不因颜色不足限制分类数量这一核心自由度）
- 矩阵中任务圆点按其所属分类做**分色切片**（类似小型饼图），多分类任务在一个点内切分显示各分类颜色
- 分类筛选在左侧菜单下区，每个分类是一个开关，**可多选累加**：选中的分类命中即显示（逻辑或），一个都不选 = 所有分类；筛选生效时命中的任务圆点依然保持分色切片显示，视觉效果与总览模式统一

## 5. 任务状态与"已错过"判定

- 普通（非循环）任务的状态由两个已有字段派生计算，**不需要额外存储字段**：
  - `deadline_at` 已过 且 `completed_at` 为空 → **已错过**（状态判定立即生效，超过截止时间的那一刻即成立）
  - 矩阵图上的"贴边展示 + 标红 + 逾期天数"是这个已错过状态在**矩阵这一视图**里的呈现方式，有 3 天的展示宽限期（见第1节边界情况），宽限期结束后任务退出矩阵图，但"已错过"这个状态判定本身不受这 3 天影响，从超期那一刻起就已经成立
- 列表内容由三个正交维度组合：**范围**（左侧菜单上区：全部 / 收藏，单选；收藏 = 标星任务）∩ **分类**（左侧菜单下区，多选的并集）∩ **状态**（清单页面内、添加栏下面一行：全部 / 未完成 / 已完成 / 已错过，单选，默认未完成），类似 Outlook 的多维度筛选而非独立收纳容器
- 矩阵模式没有状态行，只受范围与分类的选择影响（矩阵本身只显示未完成的任务）

## 6. 循环任务

- 采用业界标准 **RFC 5545（iCalendar）RRULE** 描述循环规则，使用 `rrule.js` 库处理解析和下次发生时间计算
- **循环不是独立的任务类型，是普通任务的一个开关**：打开后可设置 `recurrence_rule`（RRULE字符串）+ `dtstart`（起始时间），关闭后任务恢复为普通任务
- **接口收敛原则**：矩阵（`QuadrantClassifier`）等下游模块不感知"这是不是循环任务"，只接收任务当前的「一个代表」（重要性、紧迫度等标准字段），这个代表可能是普通任务本身，也可能是循环任务当前该处理的那一次实例——两者对矩阵而言是同一种输入形状，避免每新增一种任务形态就要给矩阵加一条判断分支
- **每个周期实例独立存在，互不阻塞**：例如「周一/周三/周五」的循环任务，某一次未完成不影响下一次正常出现（区别于"完成一次才生成下一次"的链式模型）
- **矩阵展示**：永远只显示"当前该处理的下一个未到期实例"，已经过去的实例（不管完成与否）不会以逾期状态挂在矩阵里；逾期不封顶的展示规则**只适用于普通任务**，不适用于循环任务的历史实例
- **实例记录与归档判定**：
  - 到了实例该出现的那一天，系统生成一条历史记录
  - 若到下一个实例出现时，前一个实例仍未被标记完成，系统**自动判定为"未完成"并归档**
  - 归档后的状态**并非最终结论**，用户可以随时回到该循环任务的历史列表中，手动修改某次实例的完成/未完成状态（例如事后补登记"其实那天做了，忘记点了"）
- **记录独立于配置存续**：若用户后来关闭了循环开关（甚至删除了 `recurrence_rule`），已产生的历史实例记录**不会跟着消失**，作为独立数据持续存在
- 循环任务的重要性由用户设定后，各实例继承同一重要性
- 若某任务（含循环任务实例）既无重要性也无紧迫度，不进入矩阵展示（同第3节边界情况）
