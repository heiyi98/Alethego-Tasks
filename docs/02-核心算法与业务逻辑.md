# 核心算法与业务逻辑

## 0. 坐标方向（明确约定）

矩阵坐标系并非行业统一标准（Eisenhower 本人未曾绘制过矩阵图，后世不同来源的轴线分配也不一致），本项目明确约定：

- **X 轴（紧迫度）**：越靠右越紧急
- **Y 轴（重要性）**：越靠上越重要

## 1. 紧迫度（X轴）计算

### 理论依据

人类对时间/数值差异的感知遵循 **Weber-Fechner 定律**（对数感知定律）：感知差异与刺激的相对比例相关，而非绝对差值。这与「双曲线贴现」（Ainslie, 1975；Piers Steel 的时间动机理论）描述的现象在数学上是等价的——deadline 越近，紧迫感上升越剧烈；deadline 越远，紧迫感变化越平缓。

选刻度时参考过敏捷开发故事点估算用的斐波那契数列（相邻档位比例约为黄金比例 **φ ≈ 1.618**，同样基于 Weber-Fechner 定律）：越近的档位越密、越远越疏。**斐波那契只是挑选刻度时的参考，不是实际标尺**——实际标尺是按自然天、周、月、季度取的天数（见下表），更贴近日常说法（"一周内""一个月内"），也方便以后调整。

### 判档依据：日历日，不看几点几分

- **N = (截止日期 − 今天) 的日历天数 + 1**，今天算第 1 天（N = 1），明天 N = 2，以此类推
- 日期、"今天"一律按用户时区确定
- 只选了日期的任务和设了具体时刻的任务**落格方式完全相同**：同一天截止就落在同一格，不看几点几分；循环任务用当前代表实例所在的日期（见第6节）
- 截止时刻已经过去的普通任务不按 N 判档，进入逾期区（见下文"边界情况处理"）
- 例：现在是周一 15:54——今天 23:59 截止和今天 16:00 截止都是 N = 1；明天 00:30 和"明天"（全天）都是 N = 2

### 两种模式：短期、长期

矩阵分**短期**和**长期**两种模式，默认短期。矩阵上方单独一行有一个文字胶囊，显示当前所处的模式名（"短期"或"长期"），点它切换到另一个模式；胶囊不与矩阵图占据的空间重叠。矩阵本身没有外框，和页面背景融为一体。

- 两种模式都是 **6 个等宽的格子**，竖直中线在这 6 格的正中；切换模式时中线的位置不动
- **逾期区**不算在 6 格里，是接在 6 格最右边的额外一段，宽 **1/4 格**；所以整张图右边比左边多出这一截，中线仍在 6 格正中
- 刻度名标在**分界线上**，不标在格子中央；逾期区没有刻度、不写字
- 各格 N 的上界按自然天、周、月、季度取值，集中在代码的具名常量里（`packages/core/src/urgency/tiers.ts`），调整刻度只改一处

**短期模式（今天到两周）**，从左到右：

| 格子 | 日历天数 N | 格子左右两侧的刻度名 | 所在侧 |
|---|---|---|---|
| 1 | 8–14 | 两周 — 一周 | 不紧急 |
| 2 | 6–7 | 一周 — 5天 | 不紧急 |
| 3 | 4–5 | 5天 — 3天（中线） | 不紧急 |
| 4 | 3 | 3天（中线） — 2天 | 紧急 |
| 5 | 2 | 2天 — 1天 | 紧急 |
| 6 | 1（今天） | 1天 — 逾期区 | 紧急 |

刻度名从左到右：两周、一周、5天、3天（中线）、2天、1天。N > 14 的任务在短期模式的图上不显示。

**长期模式**，从左到右：

| 格子 | 日历天数 N | 格子左右两侧的刻度名 | 所在侧 |
|---|---|---|---|
| 1 | 91–180 | 半年 — 一季度 | 不紧急 |
| 2 | 31–90 | 一季度 — 一个月 | 不紧急 |
| 3 | 15–30 | 一个月 — 两周（中线） | 不紧急 |
| 4 | 8–14 | 两周（中线） — 一周 | 紧急 |
| 5 | 4–7 | 一周 — 3天 | 紧急 |
| 6 | 1–3 | 3天 — 逾期区 | 紧急 |

刻度名从左到右：半年、一季度、一个月、两周（中线）、一周、3天。N > 180 的任务在长期模式的图上不显示。

对照（现在是周一）：
- 短期：周一 → 1天以内；周二 → 2天–1天；周三 → 3天–2天；周四、周五 → 5天–3天；周六、周日 → 一周–5天；下周一到下周日 → 两周–一周；再往后的不显示
- 长期：周一到周三 → 3天；周四到周日 → 一周；下周一到下周日 → 两周；第 15–30 天 → 一个月；第 31–90 天 → 一季度；第 91–180 天 → 半年；更远的不显示

**紧急/不紧急分界跟着当前模式**：中线右边三格为「紧急」——短期 **N ≤ 3**，长期 **N ≤ 14**；逾期一律紧急。`QuadrantClassifier` 带模式参数，按同一规则判定象限；矩阵下方的四象限清单分组时也用当前模式的判定。重要/不重要的判定与模式无关。

**四象限清单里显示哪些任务与模式无关**：图上不画的（例如短期模式下 N > 14 的任务）照样出现在清单里；只有远期（N > 365）、没有截止时间的随意任务、逾期满 3 天的不进清单。

### 圆点与标签

- **圆点才是任务的位置**，永远在它所属的格子里：每个任务按自己的 id 得到一个固定偏移，横竖都落在所属格子（× 重要性一行）的内部，不贴格子边和刻度线，刷新不会跳动；偏移后圆点仍靠得太近，就在格内错开，直到互不重叠
- **标签**没有外框、没有背景：标题文字写在一条细横线上，另用一条细线连回自己的圆点；字和线同色，逾期任务用红色。标题最大宽度统一为 45ch（1ch = 当前字体里"0"的宽度，随字号变化），所有语言用同一个宽度，超出按量出来的宽度截断加省略号，不按字符数截断。标签可以伸出格子
- **标签位置用力导向算法**（`packages/core/src/matrix/label-layout.ts`），不预先规定标签在圆点的哪个方向，可以在上下左右及斜向：
  - 所有标签同时参与迭代：标签之间重叠时互相推开；压到圆点时被推开；别人的连线穿过时让开；一根弹簧把标签拉回自己圆点附近；不出图的范围
  - 迭代中途把连线交叉的两个标签交换位置（交换后交叉变少，或交叉不变但连线总长变短），直到连线互不交叉
  - 迭代结束仍有冲突的标签，在自己圆点周围一圈圈固定的候选位置里挑冲突最少的
  - 目标依次是：连线不交叉、标签不压圆点、标签互不重叠、连线不穿过别的标签。达到迭代上限仍有重叠时允许标签间轻微重叠，但连线不交叉，圆点画在最上层、互不遮挡、始终完全可见，不省略任何任务
  - 没有随机成分：同样的数据每次渲染结果完全相同，与任务的先后顺序无关
- 点击标签或圆点弹出编辑面板；点击范围就是标签本身，不为扩大点击区域放大标签

### 扩展向量（超过一年）

| 日历天数 N | 说明 |
|---|---|
| 366–730 | 两年内 |
| 731–1095 | 三年内 |
| 1096–1825 | 五年内 |
| 1826–2555 | 七年内 |
| 2556–3650 | 十年内 |

同样是自然值。紧迫度数值上仍按此延伸计算，但 **N > 365 的任务不进入矩阵视图**（图与四象限清单都不显示），仅在列表视图中正常呈现。

### 边界情况处理

- **无截止时间**（但设了重要性）：两种模式都显示，圆点贴在图的**最左边缘**（完整可见），竖向仍按重要性放进对应区间；算不紧急。没有截止时间的随意任务不进矩阵（见第3节）
- **逾期区**（只针对普通任务）：截止时刻一过就算逾期——只选日期的从截止日期的次日 00:00 起，设了时刻的从那个时刻起（包括今天稍早已过的时刻）
  - 逾期就是逾期：一个区，宽 1/4 格，接在 6 格最右边，两种模式都有；不分道，不画刻度，不写任何文字，淡红底色
  - 圆点在这一小条里按重要性竖向定位（横向按 id 固定偏移），互不重叠；圆点保留分类颜色，外加红色外圈；标签在圆点左边（圆点在标签右端），红色
  - 逾期满 **3 天**的任务退出矩阵图，只在清单的"已错过"里可见（天数是具名常量 `OVERDUE_MATRIX_GRACE_DAYS`）。这 3 天只是矩阵上的展示宽限期，"已错过"状态本身在超过截止时间的那一刻就已成立，见第5节
  - 循环任务永远不进逾期区（见第6节）

### 关键实现原则

紧迫度**不是**创建任务时计算一次存死的值，而是**每次展示时基于当前时间动态计算**（因为距截止时间的天数会随时间推移变化）。

## 2. 重要性（Y轴）

- 用户手动选择，**四档**，由强到弱：**必须、应该、可以、随意**（英文 Must / Should / Could / Optional；多语言以英文为翻译标杆，文案集中在 `apps/web/src/i18n`，每档一个文案键 `must / should / could / optional`）
- 存储为 0–3：0 = 随意、1 = 可以、2 = 应该、3 = 必须（`packages/core` 的 `domain/importance.ts`）
- **"随意"是默认档**，新建任务不选就是它；不再有"未设置重要性"
- 各档的判断标准（只写在文档里，界面上不加说明）：
  - **必须**：不做会造成严重后果，或者整件事失败
  - **应该**：很重要，不做会很痛，但有替代办法，或者可以晚一点
  - **可以**：做了有好处，不做影响很小
  - **随意**：做不做都可以
- 组任务也有这四档重要性，由能编辑任务的人（项目管理员；合作组里人人都是管理员）设定，全组共用
- 矩阵上每一档对应 Y 轴一条固定区间，任务在该区间内自由散布，不强制对齐某个精确坐标点
- 矩阵纵轴共 4 格：刻度 0 到 3 标在分界线上（只写数字，不写文字），重要性 N 落在标 N 那条线上方的一格（N = 3 是最上面一格，顶端不再标"4"）；中线在刻度 2 上（"应该"和"可以"之间），下面两格是随意、可以（不重要），上面两格是应该、必须（重要）

## 3. 象限判定逻辑与矩阵展示规则

- 象限是根据「紧迫度所属区（紧急/不紧急）× 重要性所属区（重要/不重要）」计算得出的展示分组，不存储为任务字段，属于查询/展示层的派生逻辑
- **四个象限均为合法区域**，包括"不重要且不紧急"——一个"可以"、紧迫度落在不紧急区的任务，会正常显示在矩阵左下角区域，这不代表它被排除
- **唯一不进入矩阵坐标系的情况**：没有截止时间**且**重要性是"随意"。没有截止时间但档位更高的，仍然钉在最左边，按档位放在对应的行
- 远期（扩展向量，超过一年）任务不进入矩阵视图，即使有明确的重要性设置；超出当前模式范围（短期 N > 14，长期 N > 180）的任务图上不画，但仍在四象限清单里
- 矩阵图不绘制可见网格线，格子仅为逻辑上的坐标范围；同一（重要性区间 × 紧迫度区间）内的多个圆点在格内错开、互不重叠，标签排布见第1节"圆点与标签"

## 4. 分类（多对多）

- 一个任务可同时归属**多个**分类，数据层面是标签（多对多关系），但 UI 呈现上让用户感觉是"归属"体验（参考邮箱的多收件箱模式：删除分类只解除关联，不影响任务本身存续）
- 每个分类需要一个**颜色属性**，用于矩阵中任务圆点的分色标识：
  - 提供默认调色板候选（起步九色：红黄蓝、橙绿紫、粉棕青），颜色之间视觉独立性强
  - 提供自定义调色板（优先级低，可复用现成的颜色选择组件）
  - 颜色需在用户的分类集合内**排他，不重复**；调色板耗尽后的处理方式留待实现阶段决定（建议方向：不因颜色不足限制分类数量这一核心自由度）
- 矩阵中任务圆点按其所属分类做**分色切片**（类似小型饼图），多分类任务在一个点内切分显示各分类颜色
- 分类筛选在左侧菜单下区，每个分类是一个开关，**可多选累加**：选中的分类命中即显示（逻辑或），一个都不选 = 所有分类；筛选生效时命中的任务圆点依然保持分色切片显示，视觉效果与总览模式统一

## 5. 任务状态与"已错过"判定

- 普通（非循环）任务的状态由两个已有字段派生计算，**不需要额外存储字段**：
  - `deadline_at` 已过 且 `completed_at` 为空 → **已错过**（状态判定立即生效，超过截止时间的那一刻即成立）
  - 矩阵图上的逾期区是这个已错过状态在**矩阵这一视图**里的呈现方式，有 3 天的展示宽限期（见第1节边界情况），宽限期结束后任务退出矩阵图，但"已错过"这个状态判定本身不受这 3 天影响，从超期那一刻起就已经成立
- 列表内容由三个正交维度组合：**范围**（左侧菜单上区：总览 / 收藏，单选；总览 = 不选任何分类、看全部任务，点"总览"会清空分类选择；收藏 = 标星任务）∩ **分类**（左侧菜单下区，多选的并集）∩ **状态**（清单页面内、添加栏下面一行：全部 / 未完成 / 已完成 / 已错过，单选，默认未完成），类似 Outlook 的多维度筛选而非独立收纳容器
- 矩阵模式没有状态行，只受范围与分类的选择影响（矩阵本身只显示未完成的任务）
- **待确认**（只有开了任务分配的项目）：R 标记完成后、A 确认之前的状态（`completed_at` 有值、`confirmed_at` 为空）。待确认期间截止时间过了也不算已错过；"已完成"只包括已确认的任务；开了任务分配的项目（以及有这样的项目的组页面）状态行多一个"待确认"，个人和没开任务分配的项目没有这一项
- **在组里**：组页面的列表内容 = 这个组里我能看到的所有项目的任务 ∩ 状态；项目页面 = 这个项目的任务 ∩ 状态；范围和分类不起作用

## 6. 循环任务

- 采用业界标准 **RFC 5545（iCalendar）RRULE** 描述循环规则，使用 `rrule.js` 库处理解析和下次发生时间计算
- **循环不是独立的任务类型，是普通任务的一个开关**：打开后可设置 `recurrence_rule`（RRULE字符串）+ `dtstart`（起始时间），关闭后任务恢复为普通任务
- **接口收敛原则**：矩阵（`QuadrantClassifier`）等下游模块不感知"这是不是循环任务"，只接收任务当前的「一个代表」（重要性、紧迫度等标准字段），这个代表可能是普通任务本身，也可能是循环任务当前该处理的那一次实例——两者对矩阵而言是同一种输入形状，避免每新增一种任务形态就要给矩阵加一条判断分支
- **每个周期实例独立存在，互不阻塞**：例如「周一/周三/周五」的循环任务，某一次未完成不影响下一次正常出现（区别于"完成一次才生成下一次"的链式模型）
- **代表实例**：循环任务的代表 = **时刻还没过的最早一个未完成实例**，截止时刻就是这个实例的时刻。当前实例的时刻一过（不是等到午夜），代表立刻换成下一次；在清单里勾选"完成本次"后也立刻换成下一次。清单与矩阵用同一个代表
- **矩阵展示**：只显示代表实例，按它所在的日历日判档；已经过去的实例（不管完成与否）不会挂在矩阵里——**循环任务永远不进逾期区**，逾期区只适用于普通任务
- **实例记录与归档判定**：
  - 实例的时刻一过、仍未勾选完成，系统**立刻**生成一条历史记录并判定为"未完成"（不等下一个实例出现）
  - 补记录的起点：第一次从开始时间起补；之后从已有记录中时刻已过的最新一条往后补。**开始时间本身改了**时，从新的开始时间补齐缺的记录（已有记录不动）
  - **改循环规则**（频率、间隔、星期、结束条件）：已发生的记录保持不变，新规则只管以后到点的实例（从已有记录中最新的一条之后开始记）
  - 归档后的状态**并非最终结论**，用户可以随时在展开面板里的历史中修改某次实例的完成/未完成状态（例如事后补登记"其实那天做了，忘记点了"）
  - 提前勾选完成的实例同样记为一条"已完成"记录，代表随即顺延到下一次
- **编辑范围**：编辑器只支持"每 N 天""每 N 周（可选星期几）"，以及结束条件与开始时间。库里已有的每月/每年等其他规则数据保持不动，引擎照常计算；编辑器按"超出可编辑范围的规则"处理（只显示规则原文，不能在编辑器里修改）
- **历史**：嵌在展开面板里（重复规则下方），不单独开页面。纵向列出最近两次已过去的实例（最新在上），每行是日期、星期、时刻和一个勾选框（勾上 = 已完成，不勾 = 未完成）；已完成的记录沿用任务行现有的"已完成"样式（删除线、变灰），没做的按"已错过"的样式显示（日期标红），这只是外观；右侧的向下三角展开到五行高、可上下滚动看到全部更早的记录（可能有几百条），再点收起
- **记录独立于配置存续**：若用户后来关闭了循环开关（甚至删除了 `recurrence_rule`），已产生的历史实例记录**不会跟着消失**，作为独立数据持续存在
- 循环任务的重要性由用户设定后，各实例继承同一重要性
- 若某任务（含循环任务实例）没有截止时间且是"随意"，不进入矩阵展示（同第3节边界情况）

## 7. 组、项目：身份、工具箱、RACI 与完成确认

- **结构**：组是项目的容器；组任务必须属于一个项目。项目有名字、颜色和工具箱
- **功能集中配置**（`packages/core/src/domain/group.ts`）：
  - `GROUP_KIND_CONFIG`：组的类型只决定身份结构——合作组人人都是组长（所以在每个项目里都是管理员，只在项目里的人也是管理员）；管理组分组长、管理员（项目上的身份）、组员；被邀请进组的人的身份；投票超时
  - `TOOL_FEATURES`：每个工具打开的功能。任务分配 → RACI、完成确认（待确认）、只有名字的人、任务通知、责任分配矩阵；任务关系这一轮只记录选择
  - `featuresForProject(project)` 按工具箱合成一个项目的功能；个人是 `PERSONAL_FEATURES`（清单 + 时间管理矩阵；重要性、分类、收藏）；`featuresForGroupPage(projects)` 是组页面（只有清单；有一个项目开了任务分配就有待确认）
  - 各种看法（清单、时间管理矩阵、责任分配矩阵、甘特图）都从同一份数据取任务（`TaskDataProvider` + `useVisibleTasks`），各自只负责怎么画（`apps/web/src/views/registry.tsx` 登记）
- **身份**：组长自动在每个项目里、不能被移出、不能退出项目，在项目里等同管理员；只有组长能建项目、任命 / 撤销项目管理员、邀请人进组、踢出组、任命新组长、删除组和项目。管理员只在被任命的项目里有效：建、改、删任务，设 RACI，往项目里加人、移出组员，添加和删除只有名字的人。组员开了任务分配时按 RACI，没开时只能标记完成。项目的任务只有项目成员看得到
- **RACI**（开了任务分配）：R 负责做，能标记完成；A 能确认完成、也能不通过；C 被咨询（目前只是标注）；I 被告知（项目成员的 I 在任务状态或内容变化时收到通知，只有名字的人只是标注）。每个字母不限人数；R、A 必须是项目成员；创建任务的人默认是 A；由项目管理员设定
- **完成确认**（开了任务分配）：R 标记完成 → 待确认；任意一个 A 确认 → 已完成；A 不通过 → 回到未完成。R 和 A 是同一个人、或任务没有 A 时，标记完成直接算已完成。循环任务这一轮不需要 A 确认。没开任务分配：项目成员都能标记完成，完成即确认
- **投票**：删除组、删除项目、任命组长都要全体组长同意；发起者算同意，一个不同意就取消（之后可以重新发起），超时不操作算同意（删除组和项目一周、任命组长三天）。投票期间新成为组长的人也要同意或等到超时。没有后台定时任务：任何成员打开 TaskApp 时检查一次是否超时
- **移出、踢出与退出**：移出项目时，开了任务分配、他在这个项目里有 R 或 A 就不行，先改 RACI；没有时确认后一并去掉他在这个项目里的 C、I；没开任务分配直接移出。踢出组 / 退出组覆盖他所在的所有项目。最后一位组长不能退出管理组（先任命新组长，或删除组）；合作组最后一个人退出时组和项目、任务一起删除
- **执行人和负责人必须有**：开了任务分配的项目里的任务至少要有一个执行人（R）和一个负责人（A），建任务时就要选；之后也不能删光
- **通知**：数据库只记结构化信息（操作者、动作、对象、任务、项目、改动的字段），前端拼成一句话，文案集中在 `apps/web/src/i18n/`（以后加语言只需再写一份）。任务通知只在开了任务分配的项目里：设为执行人 → 被设的人、知会；完成 → 负责人、知会；确认 / 退回 / 修改 → 执行人、知会；只发给项目成员、不发给自己。同一个人、同一条任务、同一种通知在处理之前只保留一条，再次修改时合并改动的字段并更新时间。入组邀请、项目邀请发给被邀请的邮箱；删除组、删除项目、任命组长的投票发给其他组长

## 8. 任务关系：两行逻辑、等待、浮动时间和关键路径

都在 `packages/core/src/schedule`（纯 TypeScript，各自独立、有单元测试），以天为单位（`calendar-date`，"YYYY-MM-DD"）：

- **两行逻辑的日期推算**（`schedule-dates`）：
  - 开始 = 固定日期，或者关系里最晚的（对方的日期 + 偏移）；结束 = 固定日期（截止时间所在的日期），或者关系里最晚的，或者开始 + N 天（开始为空时结束也为空）
  - 对方的"开始"没有时按它的结束日期（里程碑）；对方没有日期的关系不算；一个都算不出来时为空
  - 开始和结束是同一天、只有开始、或者只有结束：里程碑（甘特图上是那天线上的菱形）
  - 数据库里有同样的算法（触发器），是最终结果；前端这份用于预览、等待和甘特图
- **循环检测**（`relation-cycles`）：只看任务之间的依赖，不分开始和结束；让 A 依赖 B 时从 B 往上找，能找回 A 就是循环；也提供拓扑排序
- **等待**（`waiting`）：只看还没完成的任务
  - 等对方"结束"：对方已确认完成（开了任务分配的项目以负责人确认为准；其他地方完成即确认）
  - 等对方"开始"：对方已完成；或者对方有开始关系时，它等的那些事都已发生（逐层往上判断）；或者对方是固定开始日期且已到那天；对方没有开始条件算已开始
  - 先列开始那一行的关系，再列结束那一行的；看不到的、已删除的关系对象不挡人
  - 可以只看某一行（`sides`）：清单的简介行只看开始那一行
- **浮动时间和关键路径**（`critical-path`）：
  - 范围是当前甘特图（这个项目或这个分类）里有日期的任务；终点 = 范围里最晚的结束日期
  - 工期 = 结束 − 开始（按现在的日期不变；没有开始的按 0）
  - 按拓扑倒序往前推：没有后续的任务最晚结束 = 终点；对每个后续，它那一侧（开始或结束）的最晚日期 − 偏移，就是这个任务对应那一侧（开始或结束）的最晚日期，取最小
  - 浮动 = 最晚结束 − 结束；浮动不大于 0 的在关键路径上
- **甘特图的排布**（`apps/web/src/lib/gantt-layout.ts`）：每一天是一条竖线，第 i 天的线在 (i + 0.5) × 两天的距离；
  任务条从开始那天的线到结束那天的线（长度 = 天数差 × 两天的距离），同一天结束和开始的任务在同一条线上；
  两天的距离按 em 定（日 2.5em、周 0.9em、月 0.3em），画的时候按页面的字号换成像素
- **时区**：结束日期是截止时间在用户时区里的日期；算出的结束写成那天的最后一刻（和"没选时刻 = 当天最后一刻"一致）

## 9. 今日、和我有关的组任务、矩阵筛选、子任务

- **和我有关的组任务**（`isRelatedGroupTask`，`packages/core/src/list/task-list-filter.ts`）：开了任务分配的项目里，我是执行人（R）的任务；没开任务分配的项目里，我所在项目的全部任务（我看得到的组任务都在我所在的项目里）
- **今日**（`isTodayTask`）：今天截止的任务（不管完成没有），以及逾期不满 3 天、还没完成的任务。"逾期天数"和矩阵逾期区一样按日历天算（`calendarDaysBetween`），满 `OVERDUE_MATRIX_GRACE_DAYS`（3）天离开今日，和离开矩阵是同一个时刻。循环任务看当前代表实例（代表实例永远是时刻还没过的那一次，所以循环任务只会"今天截止"，不会逾期）。范围 = 个人任务 + 和我有关的组任务；之后照常按状态行筛选
- **矩阵筛选栏**（`packages/core/src/matrix/matrix-filter.ts`）：存成 `{ personal, categories, groups, projects }`
  - `personal`：全部个人任务（包括没有分类的）；为 false 时只看 `categories` 里的分类（命中其一即显示）
  - `groups`：整组勾选（以后新建的项目也算）；`projects`：单独勾选的项目。组的勾选框是"已勾 / 部分 / 没勾"三态；只勾组里部分项目时组显示部分选中；组里的项目全勾上就等于整组勾选
  - 一条组任务在矩阵里：它的项目被勾选（整组或单独），并且是和我有关的组任务
  - 第一次进入（账号上还没存过，`users.matrix_filter` 为 null）时只勾"个人"；每次改勾选都存回账号
- **子任务**（`packages/core/src/domain/subtask.ts`，数据库 `task_subtasks` / `task_subtask_checks`）：
  - 普通任务：清单是没删除的子任务；勾选不分次
  - 循环任务：勾选属于每一次重复（按那一次的时刻存）。某个子任务算不算某一次里的：那一次之前就有、那一次之后才删（`subtaskApplies`，数据库里同名函数 `subtask_applies`），所以改清单只影响以后，过去各次保持原样。提前完成的那一次，清单定格在完成的时刻（`occurrenceListAsOf`）：完成之后再改清单，不影响它的历史进度
  - 父任务（或循环任务的这一次）直接勾完成时，那一次没勾的子任务一起勾上（触发器 `tasks_check_subtasks` / `occurrence_check_subtasks`）；勾完全部子任务不会让父任务自动完成；取消完成时子任务的勾选不变
  - 进度 = 这一次勾上的 / 这一次的子任务总数（`subtaskProgress`）
