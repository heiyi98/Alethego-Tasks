# 账户系统说明（Alethego Tasks 现状，供 Mindo 对齐）

本文说明 Alethego Tasks（下称 TaskApp）现在的账户系统：谁负责登录、令牌怎么用、用户资料存在哪里、多账号和退出怎么做、国际 / 中国大陆两种部署的差别。最后一节列出 Mindo 对齐时要改和不要动的地方。

更细的背景见《账号与多产品体系文档》（docs/05）和《身份对接说明》（docs/06）；部署见《部署说明》（docs/08）。

## 1. 总体结构：一个身份项目，各产品只验证令牌

```
【Alethego 身份项目】  https://ibtwrccctdsqdygjebsp.supabase.co
  只负责：注册、登录（邮箱密码、Google）、签发 access token、续期
        │  access token（sub = 用户编号，带 email）
        ├──────────────────────────────┐
        ▼                              ▼
【TaskApp 的数据】                 【Mindo 的数据】
  目前在 Mindo 项目的 taskapp schema   Mindo 项目自己的 schema
  只验证 Alethego 的令牌，不签发        （对齐后同样只验证 Alethego 的令牌）
```

- **账号互通，内容不互通**：同一个 Alethego 账号可以登录 TaskApp 和 Mindo；两个产品的业务数据完全分开，各自建自己的用户资料表。
- **产品不签发令牌**：TaskApp 不做换证、不自己签发凭证、不持有任何签名密钥。数据所在的 Supabase 项目通过 **Third-Party Auth（第三方认证）** 登记信任 Alethego 签发的令牌。
- Mindo 项目已经做过这项登记（TaskApp 的数据现在就放在 Mindo 项目里、靠它工作）。这项登记是项目级设置，Mindo 自己也可以直接使用。

## 2. Alethego 身份项目

- 登录方式：邮箱密码（登录 / 注册）、Google 登录（OAuth，PKCE 流程）。
- Redirect URLs：TaskApp 的正式域名和预览域名已加入；Google 登录完成后回到发起登录的那一页。Mindo 的域名也需要在这里（如果还没有）。
- access token 里的关键字段：
  - `sub`：用户编号。各产品里 `auth.uid()` 就是它，也是各产品用户资料表的主键。
  - `email`：用户邮箱。TaskApp 的入组 / 入项目邀请按邮箱认人，用的是 `auth.jwt() ->> 'email'`。
  - `user_metadata`（例如 Google 登录带来的 `full_name`）：TaskApp 只在第一次建用户资料时用它当默认名字。
- Alethego 里只放通用的账户信息，不放任何产品的业务字段。

## 3. 数据项目这一侧（以 TaskApp 为例）

### 3.1 令牌验证

- 数据项目登记了第三方认证（信任 Alethego 的令牌）。前端带着 Alethego 的 access token 直接请求数据项目的 Data API。
- `auth.uid()` = Alethego 的用户编号；`auth.jwt()` 是 Alethego 签发的完整声明。
- 数据项目的 `auth.users` 里**没有**这些用户的记录，所以业务表的外键都指向产品自己的用户资料表，不指向 `auth.users`。

### 3.2 用户资料：每个产品一张自己的表

TaskApp 的表是 `taskapp.users`：

```sql
create table taskapp.users (
  id                    uuid primary key default auth.uid(),  -- = Alethego 用户编号
  email                 text,
  display_name          text not null check (btrim(display_name) <> ''),
  created_at            timestamptz not null default now(),
  updated_at            timestamptz not null default now(),
  notifications_seen_at timestamptz                          -- TaskApp 自己的字段
);
```

登录后、读写任何业务数据之前，前端先调用一次：

```sql
-- 还没有这一行就创建（display_name 用传入的默认值）；已有则只更新 email
create function taskapp.ensure_current_user(p_email text, p_display_name text)
returns taskapp.users
language sql
set search_path = ''
as $$
  insert into taskapp.users (id, email, display_name)
  values (auth.uid(), p_email, p_display_name)
  on conflict (id) do update set email = excluded.email
  returning *;
$$;
```

规则：

- 默认名字：优先用 Alethego 登录信息里的名字（`full_name` / `name` / `display_name`，Google 登录会有），没有就用邮箱 @ 前面那一段。
- `email` 每次登录按 Alethego 的最新值更新；`display_name` 创建后**只由用户在 TaskApp 里改**，不再被 Alethego 覆盖。所以同一个人在 TaskApp 和 Mindo 里可以有不同的名字。
- 组里还有"本组昵称"（`group_members.nickname`），为空时显示 `display_name`。
- 这个函数以调用者身份执行（不是 security definer），仍受 RLS 约束。

### 3.3 RLS

- 所有策略只对 `authenticated` 开放；`taskapp.current_owner_id()` 只读 `auth.uid()`。没登录（只带 apikey）什么都读不到。
- `taskapp.users` 每个人只能读写自己那一行。别人的名字（组员名单、通知里的操作者）通过 security definer 的函数读取，函数里先检查调用者有没有权限看。

## 4. 前端（TaskApp 的做法）

登录相关的代码全部集中在 `apps/web/src/auth/`，任务功能只通过 `useCurrentUser()` 取当前用户（编号、邮箱、名字、取 access token 的函数）。

### 4.1 两个 client

| client | 连哪里 | 用什么 key | 做什么 |
|---|---|---|---|
| 登录 client | Alethego | Alethego 的 publishable key | 登录、注册、保存会话、自动续期 |
| 数据 client | 数据项目 | 数据项目自己的 key | 读写业务数据；每次请求带上登录 client 当前的 access token |

数据 client 用 supabase-js 的 `accessToken` 选项拿令牌：

```ts
const dataClient = createClient(DATA_URL, DATA_KEY, {
  db: { schema: 'taskapp' },
  accessToken: async () =>
    (await loginClient.auth.getSession()).data.session?.access_token ?? null,
});
```

登录 client 的设置：`persistSession: true`、`autoRefreshToken: true`、`flowType: 'pkce'`。只有登录页用的临时 client 处理地址栏里 Google 登录带回来的授权码（`detectSessionInUrl`）。

### 4.2 会话与续期

- 会话到期自动续期（登录 client 的 `autoRefreshToken`；数据 client 每次取令牌时快到期的会话会先续期）。用户不会被要求定期重新登录，只有主动退出才要重新登录。
- 续期失败（例如会话在别处被撤销）时，这个账号从本机列表里去掉，改用下一个账号或回到登录页。

### 4.3 一台设备多个账号

- 每个登录过的账号各有一个登录 client，会话各存一份，存在浏览器 localStorage：
  - 账号列表：`alethego-tasks.accounts`（有哪些账号、当前是哪个、显示用的名字）
  - 每个账号的会话：`alethego-tasks.auth.<用户编号>`
  - 登录页用的临时会话：`alethego-tasks.auth.pending`（不续期；拿到会话后立即转存给该账号自己的 client，并清掉）
- 侧边栏最下面的账号菜单：显示当前账号名字；点开可以直接切换到这台设备上登录过的其他账号（不用再输密码）、原地改名字（点 ✓ 或回车保存）、添加账号、退出。
- 切换账号时整个任务界面重新加载，不会带着上一个账号的数据。

### 4.4 退出

- "退出"退出这台设备上的**所有** TaskApp 账号：对每个账号调用 `signOut({ scope: 'local' })`（只撤销这一个会话的续期凭证），并清掉本机保存的会话和账号列表。
- **只退出 TaskApp 自己**，不做跨产品的一起退出，也不影响同一账号在其他设备、其他产品上的会话。目前没有"只退出其中一个账号"。

## 5. 国际 / 中国大陆

- 环境变量 `NEXT_PUBLIC_REGION`：`international`（默认）或 `china`。构建时决定。
- `china`：登录页**不显示 Google 登录**，只有邮箱密码登录 / 注册。其余完全相同。
- 浏览器端除了登录和数据两个 Supabase 地址，不请求任何外部服务（系统字体，没有 CDN、统计、地图），所以中国大陆部署不需要替换别的资源。
- 两侧数据和账号完全分开（法律要求）：中国大陆用自己的身份项目和数据项目，不和国际侧互通。
- **登录和数据也可以是同一个 Supabase 实例**：两个地址、两个 key 填同一个即可。这时用的是这个实例自己的 Auth（不需要第三方认证登记），`auth.uid()`、`auth.jwt() ->> 'email'` 照常可用。TaskApp 已在本地按这种方式跑通注册、登录、读写、组和邀请（端到端测试）。这为中国大陆在不支持第三方认证的托管服务上部署留了后路。

## 6. 环境变量（前端）

| 变量 | 说明 |
|---|---|
| `NEXT_PUBLIC_ALETHEGO_URL` | 登录用的 Supabase 地址（Alethego） |
| `NEXT_PUBLIC_ALETHEGO_PUBLISHABLE_KEY` | 它的 publishable key |
| `NEXT_PUBLIC_SUPABASE_URL` | 数据项目地址 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 数据项目的 key |
| `NEXT_PUBLIC_REGION` | `international`（默认）/ `china` |

## 7. 给 Mindo：对齐时要做的和不要动的

建议 Mindo 对齐到同样的方式（具体实现按 Mindo 自己的代码来）：

1. **登录改走 Alethego**：Mindo 前端的登录 client 连 Alethego（URL + publishable key），不再用 Mindo 项目自己的 Auth 登录注册。
2. **数据 client 带 Alethego 的令牌**：连 Mindo 项目，用 supabase-js 的 `accessToken` 选项传入登录 client 的 access token。Mindo 项目已经信任 Alethego 的令牌，不需要再登记。
3. **用户资料表**：Mindo 用自己 schema 里的用户资料表，主键 = `auth.uid()`（Alethego 用户编号），业务表外键指向它，不指向 `auth.users`。登录后先调用一次类似 `ensure_current_user` 的函数：没有就建、有就只更新 email；名字由 Mindo 自己管。Mindo 专属的字段（例如 BaZi 偏好）只放在 Mindo 的表里，不放进 Alethego。
4. **RLS**：策略对 `authenticated`，按 `auth.uid()` 判断归属；需要按邮箱认人时用 `auth.jwt() ->> 'email'`。
5. **Mindo 现有用户**：现在 Mindo 自己 Auth 里的用户编号和 Alethego 里的不同。如果要保留 Mindo 的已有数据，需要在 Alethego 里为这些人建账号（或让他们重新注册），再把 Mindo 数据里的用户编号换成 Alethego 的编号（一次数据迁移，按邮箱对应）。内测阶段没有真实用户时，也可以直接从空开始。
6. **Redirect URLs**：Mindo 的正式域名、预览域名加进 Alethego 的 Redirect URLs（Google 登录要用）。
7. **多账号、退出（可选，和 TaskApp 保持一致）**：同一设备多账号直接切换；退出用 `signOut({ scope: 'local' })`，只退出 Mindo 自己。localStorage 的键用 Mindo 自己的前缀，不要用 `alethego-tasks.`。
8. **中国大陆**：同样用一个地区变量，`china` 时隐藏 Google 登录。

不要动的：

- **Mindo 项目对 Alethego 的第三方认证登记**：TaskApp 现在也靠它工作，删掉 TaskApp 会立刻登录不了。
- **`taskapp` schema 和 Data API 的 Exposed schemas 里的 `taskapp`**：这是 TaskApp 的全部数据，Mindo 不要读写、不要改结构。TaskApp 以后迁到自己的 Supabase 项目时，会用 `supabase/scripts/drop-taskapp.sql` 从 Mindo 项目里一次删干净（只删 `taskapp` 这个 schema，不碰 Mindo 的任何东西）。
- **Alethego 项目里的用户**：不要往 Alethego 里加 Mindo 专属字段，也不要在 Alethego 里放业务表。
