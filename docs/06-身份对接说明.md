# 身份对接说明

TaskApp 不自己管理账号：登录注册由独立的 **Alethego** 项目负责，TaskApp 只使用 Alethego 签发的 access token。本文说明现在的对接方式、代码组织，以及以后迁移时要做什么。

## 两个 Supabase 项目

| 项目 | 作用 | 前端怎么连 |
|---|---|---|
| **Alethego**（`https://ibtwrccctdsqdygjebsp.supabase.co`） | 只负责登录注册：邮箱密码、Google 登录；签发 access token | **登录 client**：用 Alethego 的 publishable key，只做登录、注册、会话保存和自动续期 |
| **数据项目**（目前是 Mindo 项目 `wsbskrgrkajnzzgpcfws` 的 `taskapp` schema） | 存 TaskApp 的全部数据；只验证令牌，不签发 | **数据 client**：apikey 用数据项目自己的 key；通过 supabase-js 的 `accessToken` 选项，每次请求带上登录 client 当前的 Alethego access token |

数据项目已通过 Supabase 的**第三方认证（Third-Party Auth）**登记信任 Alethego 签发的令牌，所以：

- 不做任何换证，不自己签发凭证，也不需要任何签名密钥；
- 带着 Alethego 的 access token 直接请求数据项目的数据接口，`auth.uid()` 就是用户在 Alethego 的编号；
- 数据项目的 `auth.users` 里没有用户记录，TaskApp 自己的用户信息放在 `taskapp.users`（见《数据模型文档》）。

## 登录与会话

- 没登录时打开网站，只显示登录页：邮箱密码（登录 / 注册）、Google 登录。
- Google 登录走 Alethego 的 OAuth 授权地址，登录完成后回到 TaskApp 当前页面（PKCE 授权码在回来时由登录 client 换成会话）。TaskApp 的正式域名和预览域名已加入 Alethego 的 Redirect URLs。
- **会话到期自动续期**：登录 client 开启 `autoRefreshToken`，数据 client 每次取令牌时（`getSession()`）快到期的会话会先续期。用户不会被要求定期重新登录，只有主动退出才需要重新登录。
- 登录后、访问任何业务数据之前，调用 `taskapp.ensure_current_user(email, 默认名字)`：
  - `taskapp.users` 里还没有这个用户就创建一行，`display_name` 默认优先用 Alethego 登录信息里的名字（Google 登录会有），没有就用邮箱 @ 前面那一段；
  - 已有这一行时只按 Alethego 的最新值更新 `email`；`display_name` 创建后只由用户在 TaskApp 里修改，不再被 Alethego 覆盖。
- RLS：所有策略只对 `authenticated` 开放，`current_owner_id()` 只读 `auth.uid()`；没登录（只带 apikey）什么都读不到。

## 多账号与退出

- 这台设备上登录过的每个账号，各有一个登录 client、各存一份会话（浏览器 localStorage，键 `alethego-tasks.auth.<用户编号>`），账号列表存在 `alethego-tasks.accounts`。因此在侧边栏最下面的账号菜单里可以直接切换账号，不需要再输密码。
- 登录页用一个临时的登录 client（键 `alethego-tasks.auth.pending`，不续期）；拿到会话后立即转存到该账号自己的 client 里，并清掉临时数据。
- "添加账号"进入登录页，登录后加入列表；"退出"退出这台设备上的所有账号（撤销这些会话在 Alethego 的续期凭证并清掉本机数据），回到登录页。
- 退出只退出 TaskApp 自己，不做跨产品的一起退出。
- 切换账号时整棵任务界面重新挂载，不会带着上一个账号的数据。

## 代码组织

登录相关的一切集中在 `apps/web/src/auth/`：

| 文件 | 内容 |
|---|---|
| `auth-provider.tsx` | 登录状态、多账号会话、续期、确保 `taskapp.users` 有这一行；对外只提供 `useCurrentUser()` |
| `login-page.tsx` | 登录页 |
| `account-menu.tsx` | 账号菜单 |
| `accounts.ts` | 本机账号列表、默认名字（纯函数，有单元测试） |
| `index.ts` | 模块出口 |

任务功能的代码只通过 `useCurrentUser()` 取当前用户（编号、邮箱、名字、取 access token 的函数），数据 client 由 `lib/repositories.ts` 用它创建。**以后如果改成跳转到 Alethego 统一登录中心，只替换 `src/auth` 这个模块。**

## 环境变量

| 变量 | 值 |
|---|---|
| `NEXT_PUBLIC_ALETHEGO_URL` | Alethego 项目地址 |
| `NEXT_PUBLIC_ALETHEGO_PUBLISHABLE_KEY` | Alethego 的 publishable key |
| `NEXT_PUBLIC_SUPABASE_URL` | 数据项目地址 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 数据项目的 key |

## TaskApp 迁到自己的 Supabase 项目时

只需在新项目上用 Supabase 的管理接口做**一次同样的第三方认证登记**（信任 Alethego 签发的令牌），然后：

1. 在新项目上执行 `supabase/migrations` 的全部迁移，并在 Exposed schemas 中加入 `taskapp`；
2. 把 `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` 换成新项目的值。

登录模块、Alethego 的配置和前端代码都不用改。

## 本地测试

单元测试和端到端测试都只用本地环境，不连真实的 Alethego / 数据项目：

- 本地数据项目：Postgres + PostgREST，已应用 `supabase/migrations`；
- 本地 Alethego：真实的 Supabase Auth（GoTrue）服务，邮箱自动确认；它签发令牌用的 JWT 密钥与本地 PostgREST 验证令牌的密钥一致，模拟"数据项目信任 Alethego 的令牌"；
- `.env.local` 里的四个变量指向这两个本地服务。端到端测试每次运行先注册一个新的主测试账号（`e2e/global-setup.ts`），账号相关用例各自注册自己的账号。
