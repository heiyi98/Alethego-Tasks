# 数据模型文档

## 用户表：users

登录由独立的 Alethego 项目负责（见《身份对接说明》），本项目的 `auth.users` 里没有用户记录。TaskApp 自己的用户信息放在 `taskapp.users`：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键，等于 `auth.uid()`，即用户在 Alethego 的编号 |
| email | text | 每次登录时按 Alethego 的最新值更新 |
| display_name | text | NOT NULL；创建时默认取 Alethego 登录信息里的名字（Google 登录会有），没有就用邮箱 @ 前面那一段；之后只由用户在 TaskApp 里修改，不再被 Alethego 覆盖 |
| notifications_seen_at | timestamptz \| null | 上次打开通知的时间；比它新的通知算未读（通知图标上的小圆点） |
| created_at / updated_at | timestamptz | |

- 登录后、访问任何业务数据之前调用 `taskapp.ensure_current_user(email, 默认名字)`：没有这一行就创建，有就只更新 email
- RLS：用户只能读、建、改自己那一行（不开放删除）
- `tasks.owner_id`、`categories.owner_id` 外键指向 `users.id`；`current_owner_id()` 只读 `auth.uid()`

## 核心表：tasks

只存放矩阵计算、筛选、排序真正需要用到的字段，保持精简：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| owner_id | uuid | 外键 → users.id（= auth.uid()）；组任务里是创建它的人 |
| group_id | uuid \| null | 所属的组（外键 → groups.id，删组时级联删除）；null = 个人任务。写入时按项目自动填写 |
| start_on | date \| null | 开始日期（有"任务关系"的任务）：固定日期，或者由关系算出（触发器写入）。没有开始时为空 |
| end_after_days | int \| null | 结束是"开始后 N 天"时的 N |
| date_zone | text \| null | 设定开始 / 结束的人的时区：算出的结束日期按它写成截止时间（当天最后一刻），关系对象的截止时间按它换算成日期 |
| project_id | uuid \| null | 所属的项目（外键 → projects.id，删项目时级联删除）；组任务必须有，个人任务为 null。建好后不能改（任务不能在容器之间移动） |
| is_starred | boolean | 收藏（只用于个人任务） |
| title | text | 任务标题 |
| description | text | 详细描述 |
| deadline_at | timestamptz \| null | 截止时间，UTC存储，可为空（为空时紧迫度按最大档/不紧急端计算，见算法文档） |
| importance_level | int | 重要性，**0-5，NOT NULL，默认 0**（0=未设置，1-5为用户主动设置档位；不再使用 null 表达"未设置"） |
| recurrence_rule | text \| null | RRULE字符串，作为任务的循环"开关"，为空即为普通任务 |
| recurrence_dtstart | timestamptz \| null | 循环起始时间 |
| completed_at | timestamptz \| null | 完成时间，null表示未完成 |
| confirmed_at | timestamptz \| null | 已确认的时间：个人、没开任务分配的项目完成即确认；开了任务分配的项目由 A 确认（有完成时间而它为空 = 待确认） |
| created_at | timestamptz | |
| updated_at | timestamptz | 用于同步冲突解决（Last-Write-Wins） |

> 注：`category_id` **不在此表中**——分类关系为多对多，见下方 `task_categories` 关联表。

### 任务状态是派生值，不额外存储字段

"待办 / 已错过 / 已完成"这三态**完全由现有字段计算得出**，不需要新增 `status` 字段：

- 已完成：`completed_at` 和 `confirmed_at` 都不为空
- 待确认（开了任务分配的项目）：`completed_at` 不为空、`confirmed_at` 为空；待确认期间截止时间过了也不算已错过
- 已错过：`deadline_at` 已过 且 `completed_at` 为空（判定立即生效，与矩阵展示的 3 天宽限期是两回事，见算法文档第5节）
- 待办：以上皆不成立

## 字段扩展原则

新的详情类字段（地点、人物等）按以下判断处理：

1. **一对一关系**：直接在 `tasks` 表加可空列。例如地点若只对应一个坐标，直接加 `location_place_id`、`location_name`、`location_lat`、`location_lng`。
2. **一对多关系**（例如一个任务关联多个相关人物）：必须用独立表，这是关系型数据库的硬性限制，不是设计偏好。
3. **需要对接外部标准API的字段**（地图、通讯录等）：即使当前一对一，只要该字段有自己的数据形状和索引需求，倾向于独立表，字段结构对齐外部API的数据结构（如 `place_id` 对应 Google Maps API，`contact_id` 对应系统通讯录API），减少未来对接时的转换成本。
4. **纯自定义、无固定结构、不对接任何外部系统的零碎信息**：使用 `custom_fields JSONB` 兜底字段。这是唯一合理使用JSONB的场景——已知结构的字段不应放入JSONB。MVP阶段暂不建此列，遇到真实需求再加（与子任务字段同样的"按需再加"处理方式）。

> 当前阶段（内测前）不必过度设计，凡是"能加列先加列"，真遇到一对多场景或表明显臃肿时再拆表。

## 扩展表示例（按需创建，不预先建立）

```
task_locations
  task_id (FK → tasks.id)
  place_id, name, lat, lng, address

task_people
  task_id (FK → tasks.id)
  contact_id, name, relation
```

详情页展示时，用统一的查询/拼装层（如 `TaskDetailAggregator`）分别查询这些扩展表并组装成详情对象；这是唯一"知道所有扩展表存在"的模块，`tasks` 核心表和其他扩展表互不感知彼此。

## 分类（已提前到 MVP）

分类不是 `tasks` 表的单一外键，而是**多对多**关系，通过关联表实现：

```
categories
  id, owner_id, name, color (hex，可以重复), description, tools (工具箱，只有 relations，建好后不能改), created_at

task_categories
  task_id (FK → tasks.id)
  category_id (FK → categories.id)
  created_at
```

- 一个任务可同时挂多个分类；`task_categories` 每一行只是一条"任务X挂了分类Y"的轻量关系记录，不包含任务的实质内容
- 删除一个分类，只级联删除 `task_categories` 中指向该分类的行，**任务本体完全不受影响**（不会连带删除任务，符合"任务不该像播放列表一样被连坐"的产品原则）
- `color` 用于矩阵可视化中任务圆点的分色标识；默认提供九色起步调色板（红黄蓝/橙绿紫/粉棕青），后续可扩展自定义调色板；不同分类（以及组）可以用同一个颜色；新建时默认取还没用过的第一个，全都用过就从头轮换
- 矩阵默认查看所有分类的任务，也可通过多选点亮分类进行筛选（命中其一即显示）

## 循环任务实例记录（recurrence_occurrences）

为支持"每个周期实例独立存在、可回溯查看历史、可手动修正状态"，循环任务需要一张独立的实例记录表，**不能**仅靠 `recurrence_rule` 动态算完即扔：

```
recurrence_occurrences
  id
  task_id (FK → tasks.id)
  occurrence_date       -- 这一次实例对应的日期
  status                -- completed / missed，到该实例该出现的时间点由系统自动判定，用户可事后手动修改
  completed_at (可空)
  created_at
```

- 到了某次实例该出现的那一天，系统生成一条记录
- 若下一次实例的时间点到达时，前一条记录仍未被标记完成，系统自动将其判定为 `missed` 并归档；用户可以随时回到该任务的历史列表里手动修正这条记录的状态
- **该表不依赖 `tasks.recurrence_rule` 是否仍然存在**——即使用户后来关闭了循环开关或清空了 `recurrence_rule`，历史实例记录依然独立保留，只在对应 `task_id` 被删除时才级联删除
- 矩阵、列表等下游视图不直接读这张表做判断，统一通过 `RecurrenceEngine` 计算出任务当前的"代表实例"，再以标准 Task 形状提供给上层（保持 `QuadrantClassifier` 等模块的接口收敛，见技术架构文档）

## 组、项目（groups、projects 与相关表）

组是和"个人"同级的任务容器，组里是一个个项目；组任务必须属于一个（且只属于一个）项目（`tasks.project_id`，`tasks.group_id` 跟着项目自动填写）。组之间什么都不共用；组里没有分类，组也不能被归进分类。组有三种类型，建组时确定、之后不能改（触发器拦截）；目前能建合作组和管理组，教育组还没开放。两种组只在身份结构上不同：合作组人人都是组长；管理组分组长和组员，管理员是项目上的身份。

| 表 | 字段 | 说明 |
|---|---|---|
| `groups` | id, kind, name, color, created_by, created_at, updated_at | kind ∈ cooperative（合作组）/ management（管理组）/ education（教育组）；color 是 #RRGGBB（和分类同一套调色板，可为空），显示在侧边栏组名前 |
| `group_members` | group_id, user_id, role, nickname, joined_at | 组名单。role ∈ leader（组长）/ member（组员）；合作组里人人都是组长。nickname 为 null 时显示他的 TaskApp 名字，只在本组生效 |
| `group_invitations` | id, group_id, email, invited_by, created_at | 邀请进组（只有组长）：按邮箱（小写），不发邮件；同一个组同一个邮箱只有一条。接受后变成成员（合作组：组长；管理组：组员），拒绝后删除 |
| `group_deletion_requests` / `group_deletion_votes` | | 删除组的投票（每组最多一个）与已同意的组长（发起者算同意）。只记同意；有人不同意时整个投票直接取消 |
| `group_leader_requests` / `group_leader_votes` | id, group_id, candidate_id, initiated_by, started_at / request_id, user_id | 任命新组长的投票（同一个候选人最多一个）与已同意的组长；规则同删除组，超时是三天 |
| `projects` | id, group_id, name, color, tools, created_by, created_at, updated_at | 组里的项目。color 和分类同一套调色板（可以重复）；tools 是工具箱：assignment（任务分配）、relations（任务关系），可以多选或都不选，建好后不能改（触发器 `projects_immutable_fields`，项目也不能换组） |
| `project_members` | project_id, user_id, role, joined_at | 项目名单（组长不在这里：组长自动在每个项目里）。role ∈ admin（管理员）/ member（组员）；合作组里项目里的人都按管理员算。可以是小组成员，也可以是只加入了这个项目的组外的人 |
| `project_invitations` | id, project_id, email, invited_by, created_at | 邀请组外的人加入项目（小组成员用邮箱加时直接加入，不发邀请）；对方在通知里同意后加入 |
| `project_deletion_requests` / `project_deletion_votes` | | 删除项目的投票，规则同删除组（全体组长，一周不操作算同意） |
| `project_contacts` | id, project_id, name, created_by, created_at | 只有名字的人（不是 TaskApp 用户），属于某个开了任务分配的项目，只能出现在 RACI 的 C 和 I 上 |
| `task_assignments` | id, task_id, role, user_id, contact_id | 任务上的 RACI（开了任务分配的项目）：role ∈ R/A/C/I，每个字母不限人数；指向项目成员（user_id）或这个项目里只有名字的人（contact_id），二者有且只有一个；R、A 只能是项目成员 |
| `task_notifications` | id, user_id, action, task_id, actor_id, target_user_id, fields, created_at, dismissed_at | 任务通知，只记结构化信息（操作者、动作、对象、任务、改动的字段），显示时再拼成句子（见下方"任务通知"） |

组任务的规则：

- 必须属于一个项目：约束 `(group_id is null) = (project_id is null)`；任务不能在个人、项目之间移动
- 不使用重要性、分类和收藏：约束 `importance_level = 0 and not is_starred`，`task_categories` 的策略只认个人任务（`owns_task` 要求 `group_id is null`）
- 组任务不进入总览、收藏、分类筛选和矩阵（前端 `buildTaskList` / `buildMatrixLayout` 按容器过滤）
- 项目里的任务只有这个项目的成员能看到（`is_project_member`：组长，或在 `project_members` 里）
- 循环实例记录、地点、人物与个人任务相同；读取权限是"能访问的任务"（`can_access_task`），改地点、人物要"能编辑的任务"（`can_edit_task`：个人任务的所有者、项目管理员）

| 标记完成 | 只有执行人 | 项目成员都能，完成即确认 |
| 待确认（状态行和角标）、负责人确认 / 不通过 | ✓ | |
| 任务通知 | ✓ | |
| 责任分配矩阵（项目页面标题右边切换） | ✓ | |
| 只有名字的人 | ✓ | |

开了"任务关系"：开始 / 结束两行逻辑、等待、甘特图（见下方"任务关系"）。个人分类也有工具箱（`categories.tools`），只有任务关系，建分类时选，之后不能改（触发器 `categories_tools_immutable`）。

### 完成确认（tasks.confirmed_at）

- 所有任务都有"已确认"的时间。个人任务、没开任务分配的项目里的任务完成即确认（触发器把 `confirmed_at` 设成 `completed_at`）
- 开了任务分配的项目（触发器 `tasks_completion_rules`）：
  - 只有 R 能标记完成；R 同时是 A、或任务没有 A 时直接算已完成，否则进入待确认（`completed_at` 有值、`confirmed_at` 为空）
  - A 确认（写入 `confirmed_at`）；多个 A 时任意一个确认就算
  - R 或 A 能取消完成；待确认时 A 取消完成 = 不通过，任务回到未完成，R 收到通知
- 内容（标题、描述、截止时间、循环、删除）只有项目管理员（含组长）能改，所有项目都一样
- 循环任务这一轮不需要 A 确认：R 完成某一次就算完成（触发器 `occurrence_completion_rules` 只检查是不是 R）
- 开了任务分配的项目里的任务（未删除）必须至少有一个执行人（R）和一个负责人（A）：建任务时用 `create_task_with_raci` 把任务、RACI、地点、人物在同一个事务里写入；之后改 RACI 也不能删到一个都不剩。检查是可延迟的约束触发器（`tasks_require_ra`、`task_assignments_require_ra`），在事务提交时执行

### 任务通知（task_notifications）

只在开了任务分配的项目里发。

| 字段 | 说明 |
|---|---|
| user_id | 收到通知的人 |
| action | assigned（设为执行人）/ completed（完成）/ confirmed（确认）/ rejected（退回）/ modified（修改） |
| actor_id | 操作者 |
| target_user_id | 对象：设为执行人时被设的人；其他动作为空 |
| fields | 修改了哪些：title / description / deadline / recurrence / deleted / restored / R / A / C / I / people / location |
| dismissed_at | 处理（查看、关掉）的时间；"完成"在任务被确认或退回后自动不再显示 |

| 动作 | 收到的人 |
|---|---|
| 设为执行人 | 被设的人、知会（I） |
| 完成 | 负责人（A）、知会（I） |
| 确认 | 执行人（R）、知会（I） |
| 退回 | 执行人（R）、知会（I） |
| 修改 | 执行人（R）、知会（I） |

- 只发给项目成员（只有名字的人只是标注），不发给操作者自己；离开项目后不再显示这个项目的通知
- 同一个人、同一条任务、同一种通知（同一个动作和对象）在处理之前只保留一条；再次发生时合并改动的字段、更新时间和操作者
- 改 RACI：新设的执行人发"设为执行人"；其他字母变了（或去掉了执行人）发"修改"；建任务时设定的 RACI、地点、人物不算修改
- 其他通知：入组邀请、项目邀请（组外的人）、删除组 / 删除项目 / 任命组长的投票
- 前端把这些结构化信息拼成句子（`apps/web/src/lib/notification-text.ts`），文案集中在 `apps/web/src/i18n/`，每一块和每个字段名都有自己的键

### 身份与权限

| | 组长 | 管理员（只在被任命的项目里） | 组员 |
|---|---|---|---|
| 在项目里 | 自动在每个项目里，不能被移出，不能退出项目 | 被加进项目 | 被加进项目 |
| 建 / 改 / 删任务、设定 RACI（开了任务分配） | ✓ | ✓ | |
| 标记完成（开了任务分配） | 是 R 时 | 是 R 时 | 是 R 时 |
| 标记完成（没开任务分配） | ✓ | ✓ | ✓ |
| 确认 / 不通过 | 是 A 时 | 是 A 时 | 是 A 时 |
| 往项目里加人、把组员移出项目 | ✓ | ✓ | |
| 把管理员移出项目、任命 / 撤销项目管理员 | ✓ | | |
| 添加 / 删除只有名字的人（开了任务分配） | ✓ | ✓ | |
| 建项目、改项目名和颜色、删除项目（投票） | ✓ | | |
| 邀请人进组、踢出组、任命组长（投票） | ✓ | | |
| 改组名和颜色、删除组（投票） | ✓ | | |
| 退出项目 | | ✓ | ✓ |
| 退出组 | ✓（管理组不能是最后一位组长） | ✓ | ✓ |
| 改自己在本组的昵称 | ✓ | ✓ | ✓ |

- 合作组人人都是组长，所以在每个项目里都是管理员；只加入了项目的组外的人，在合作组的项目里也是管理员
- 只加入了项目的组外的人：侧边栏只看到组名和自己的项目；看不到组名单
- 组长人数不限、不能被撤销；管理员人数不限
- 移出项目：开了任务分配、他在这个项目里有 R 或 A（未删除的任务）时不执行；否则一并去掉他在这个项目里的 C、I。没开任务分配时直接移出
- 踢出组 / 退出组：在组里任何项目上有 R 或 A 时不执行；否则把他移出组和组里所有项目，一并去掉他身上的 C、I、他的投票、以他为候选人的任命。合作组最后一个成员退出时组和项目、任务一起删除
- 有人离开后，若剩下的组长都已同意正在进行的投票，投票随即生效
- 这些规则都在数据库里生效：组和项目相关的写操作都通过 `security definer` 函数完成（函数里自己检查 `auth.uid()`），`authenticated` 对这些表只有读权限，`group_members` 另外只开放改自己的 `nickname` 一列；前端在 `packages/core` 的 `groupPermissions` / `groupMemberActions` / `projectPermissions` / `projectMemberActions` / `taskPermissions` 里按同样的规则决定显示哪些操作

| 函数 | 作用 |
|---|---|
| `create_group(name, kind, color)` | 建合作组或管理组，创建者成为组长 |
| `update_group(group_id, name, color)` | 改组名和颜色（只有组长） |
| `group_roster(group_id)` | 组名单：昵称、是否自己设过、是不是我、身份、邮箱（只在项目里的人看到的是空的） |
| `invite_to_group(group_id, email)` | 只有组长；返回 invited / already_invited / already_member / self |

## 任务关系（task_relations）

哪里生效：开了"任务关系"的项目里的任务；挂了至少一个开了"任务关系"的分类的个人任务（`task_has_relations`）。循环任务不参与。

| 字段 | 说明 |
|---|---|
| task_id | 挂着这个关系的任务 |
| side | start / end：挂在这个任务的开始那一行还是结束那一行 |
| predecessor_id | 关系对象（前置） |
| anchor | start / end：于对方的开始还是结束 |
| offset_days | 偏移：正数 = 后 N 天，负数 = 前 N 天（-3650 ~ 3650） |

- 两行逻辑怎么存：开始有关系 → 算出来的写进 `start_on`，否则 `start_on` 是固定日期；结束有关系或 `end_after_days` 不为空 → 算出来的写进 `deadline_at`（当天最后一刻，按 `date_zone`），否则截止时间是固定日期
- 计算（触发器 `tasks_schedule_compute`，任务每次写入时）：一行上所有关系取最晚的（对方的日期 + 偏移）；对方没有日期的关系不算；对方没有开始时按它的结束日期（里程碑）。直接改这些字段也会被算出来的值覆盖
- 级联（触发器 `tasks_schedule_cascade`）：开始、截止时间、时区变了或者删除 / 恢复，依赖它的任务逐层重新计算；它们的截止时间因此变了，在开了任务分配的项目里按现有规则发"修改了截止时间"的通知，操作者就是改动前置任务的人。关系对象被彻底删除（例如删除项目）时关系一并删掉，依赖它的任务重新计算
- 开始日期、"开始后 N 天"和其他内容一样，只有能编辑任务的人能改
- 有关系的任务（作为任何一方）不能改成循环任务
- 同样的算法在前端也有一份（`packages/core/src/schedule`），用于详情里的预览、等待、甘特图、浮动时间和关键路径

| 函数 | 作用 |
|---|---|
| `set_task_schedule(task_id, start_on, start_relations, end_after_days, end_relations, date_zone)` | 一次设定开始和结束（整组替换关系）。检查：能编辑这个任务、它有任务关系、关系对象可选（`can_relate_tasks`：同组的、我能看到的、开了任务关系的项目里的任务；或者同一个人的、挂了开有任务关系的分类的个人任务；不能是循环任务或已删除的任务）、不形成循环（`relation_creates_cycle`） |
| `task_has_relations(task_id)` / `task_anchor_date(task_id, anchor, zone)` / `relation_side_date(task_id, side, zone)` / `end_of_local_day(date, zone)` | 判断与日期换算 |

## 子任务（P2功能，暂不建表）

产品本质见《产品愿景与理念文档》：子任务是完整的 Task，只是多一层从属关系。正式引入时，通过一次明确的迁移操作，将 `tasks` 表"升级"为可容纳子任务的形态（新增可空的 `parent_task_id` 自关联外键）。当前阶段不预先加此字段——原因不只是"避免过度设计"，也因为父子任务在矩阵上如何联动表达（子任务紧迫度与父任务的关系等）尚未设计，属于 P2 阶段需要单独讨论的复杂问题。

## 权限模型

Supabase RLS 只对 `authenticated` 开放，没登录什么都读不到：

- 个人任务：`owner_id = current_owner_id()`（即 `auth.uid()`）且 `group_id is null`
- 组任务：当前用户是这个项目的成员（`is_project_member(project_id)`：组长，或在项目名单里）；不是项目成员看不到这个项目和它的任务（及其循环记录、地点、人物）
- 组：小组成员，或者只加入了组里某个项目的人能看到组（`is_group_participant`）；组名单只有小组成员能看到
- 分类及 `task_categories`：只属于个人
