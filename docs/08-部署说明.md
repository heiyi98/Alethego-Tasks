# 部署说明：在普通服务器上运行（不依赖 Vercel）

Alethego Tasks 的前端是一个 Next.js 应用，除了 Vercel，也可以用仓库根目录的 `Dockerfile` 在任何能跑 Docker 的服务器上运行。中国大陆部署也用这种方式。

## 环境变量

前端只用下面这些变量，都以 `NEXT_PUBLIC_` 开头：**构建时**写进前端代码，所以作为 Docker 构建参数（`--build-arg`）传入，改了要重新构建镜像，运行时再设没有用。

| 变量 | 必填 | 说明 |
|---|---|---|
| `NEXT_PUBLIC_ALETHEGO_URL` | 是 | 登录用的 Supabase 地址（Alethego 项目，或自己部署的 Supabase） |
| `NEXT_PUBLIC_ALETHEGO_PUBLISHABLE_KEY` | 是 | 上面那个地址的 anon / publishable key |
| `NEXT_PUBLIC_SUPABASE_URL` | 是 | 存数据的 Supabase 地址（`taskapp` schema 所在的项目） |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 是 | 上面那个地址的 anon / publishable key |
| `NEXT_PUBLIC_REGION` | 否 | `international`（默认）或 `china`。`china`：登录页不显示 Google 登录 |

运行时的变量（`docker run -e`）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `3000` | 监听的端口 |
| `HOSTNAME` | `0.0.0.0` | 监听的地址 |

构建参数（只影响下载，不进前端）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `NODE_IMAGE` | `node:22-alpine` | 基础镜像。Docker Hub 访问不了时换成能访问的镜像源里的 `node:22-alpine` |
| `NPM_REGISTRY` | `https://registry.npmjs.org` | 下载 pnpm 和依赖用的 npm 源，中国大陆可以用 `https://registry.npmmirror.com` |

## 构建与运行

在仓库根目录：

```bash
docker build -t alethego-tasks \
  --build-arg NEXT_PUBLIC_REGION=china \
  --build-arg NEXT_PUBLIC_ALETHEGO_URL=https://<登录用的 Supabase 地址> \
  --build-arg NEXT_PUBLIC_ALETHEGO_PUBLISHABLE_KEY=<key> \
  --build-arg NEXT_PUBLIC_SUPABASE_URL=https://<数据用的 Supabase 地址> \
  --build-arg NEXT_PUBLIC_SUPABASE_ANON_KEY=<key> \
  --build-arg NPM_REGISTRY=https://registry.npmmirror.com \
  .

docker run -d --name alethego-tasks --restart unless-stopped -p 3000:3000 alethego-tasks
```

镜像里只有 Next.js 的独立输出（`output: 'standalone'`，构建时由 `NEXT_OUTPUT=standalone` 打开），不含源码和开发依赖，以非 root 用户运行。HTTPS、域名由前面的反向代理（Nginx、Caddy 等）负责，把请求转给容器的 3000 端口即可。

不用 Docker 时也可以直接在服务器上运行（需要 Node.js 22 和 pnpm）：

```bash
pnpm install --frozen-lockfile
# 设好上面的 NEXT_PUBLIC_* 环境变量（或写进 apps/web/.env.local）
pnpm --filter @alethego/web build
pnpm --filter @alethego/web start -p 3000
```

## Supabase 这一侧

- 数据库：在数据用的 Supabase 里执行 `supabase/scripts/taskapp-full-schema.sql`，把 `taskapp` 加进 Data API 的 Exposed schemas（见《迁库说明》）。
- 登录地址的 Redirect URLs 里加上这个部署的域名（Google 登录回来、确认邮件里的链接要用）。
- **登录和数据可以是同一个 Supabase 实例**：两个地址填同一个、两个 key 填同一个即可。这时用的是这个实例自己的 Auth，令牌就是它自己签发的，不需要第三方认证登记；`auth.uid()`、`auth.jwt()->>'email'`（入组邀请靠它认人）照常可用。本地测试用同一个网关地址同时提供登录和数据，中国大陆配置的端到端测试（`e2e/china.spec.ts`）在这种方式下通过。
- 登录和数据分开（现在线上的方式）时，数据项目要通过第三方认证信任登录项目签发的令牌（见《身份对接说明》）。

## 中国大陆

`NEXT_PUBLIC_REGION=china` 时登录页只有邮箱密码登录 / 注册，没有 Google 登录。

浏览器端除了上面两个 Supabase 地址，不请求任何外部服务：

- 字体：用系统字体（`-apple-system`、PingFang SC 等），不加载 Google Fonts 或其他在线字体；
- 没有外部 CDN 上的脚本、样式、图片，全部随应用一起由这台服务器提供；
- 没有统计、埋点、错误上报，没有地图或其他 Google API；
- Google 登录只有点按钮时才会跳转到 Google，中国大陆配置下没有这个按钮；
- Next.js 构建时的匿名统计在镜像里关掉了（`NEXT_TELEMETRY_DISABLED=1`），它本来也只在构建 / 服务器端，不在浏览器里。

端到端测试 `e2e/china.spec.ts` 会记录页面发出的所有请求，检查只有应用自己和配置的 Supabase 地址。

所以在中国大陆部署时，两个 Supabase 地址本身也要在大陆能访问（例如部署在大陆的自建 Supabase）。
